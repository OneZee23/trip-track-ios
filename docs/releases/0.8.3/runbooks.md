# Два ритуала, которые выполняет владелец — 0.8.3

Оба долга давние, оба руками и оба вне кода. Здесь ровно те шаги, которые надо
сделать, и — что важнее — то, что случится, если сделать их не в том порядке.

---

## 1. Резервная копия сертификата подписи (`.p12`)

**Зачем.** `Apple Distribution: Nikita Shevelev (J52AX8YA9Y)` действует до
**26 сентября 2027**, и им подписан 0.8.1 в сторе. Приватный ключ к нему
существует **в одном экземпляре — в связке ключей этого мака**. Сертификат без
приватного ключа бесполезен: скачать его заново из Apple Developer можно, а
подписать им — нет.

Умрёт диск — придётся отзывать сертификат и выпускать новый. Само по себе это
не катастрофа (уже опубликованные сборки продолжают работать), но это блокер
на любой сабмит до тех пор, пока новый сертификат не выпущен и не разложен по
машинам, а в неудачный момент — например между «залил билд» и «ревью просит
исправление» — стоит суток.

**Проверить, что ключ на месте:**

```bash
security find-identity -v -p codesigning | grep "Apple Distribution"
```

Должна быть ровно одна строка с `J52AX8YA9Y`. Если строки нет — экспортировать
нечего, и это уже не бэкап, а восстановление.

**Экспорт.** Делается через «Связку ключей» (Keychain Access), а не командой:
`security export` умеет вынуть сертификат, но для пары «сертификат + приватный
ключ» в формате `.p12` системный диалог всё равно попросит пароль, и в
безголовом режиме это не работает.

1. Открыть **Keychain Access** → слева «Вход» (login) → вкладка «Мои
   сертификаты».
2. Найти `Apple Distribution: Nikita Shevelev (J52AX8YA9Y)`.
3. **Раскрыть треугольник слева от строки** и убедиться, что под сертификатом
   лежит приватный ключ. Если ключа нет — экспорт даст `.cer`, а не `.p12`, и
   это будет бесполезный файл с правильным именем.
4. Правой кнопкой по СТРОКЕ СЕРТИФИКАТА → «Экспортировать…» → формат
   **Personal Information Exchange (.p12)**.
5. Пароль на архив — задать и **сохранить в менеджере паролей рядом с самим
   файлом**. `.p12` без пароля невозможно импортировать, а забытый пароль
   делает копию такой же бесполезной, как её отсутствие.

**Куда положить.** Не на этот мак. Минимум — в менеджер паролей (1Password,
Bitwarden — файлом-вложением) или в зашифрованный архив в облаке. Второй
экземпляр на внешнем диске лишним не будет.

**Проверить, что копия рабочая.** Единственная честная проверка — импорт на
другой машине (или в отдельную связку):

```bash
security create-keychain -p test /tmp/check.keychain
security import ~/Downloads/triptrack-distribution.p12 -k /tmp/check.keychain -P '<пароль>'
security find-identity -v /tmp/check.keychain     # должна появиться та же строка
security delete-keychain /tmp/check.keychain
```

Непроверенный бэкап — это не бэкап, а надежда.

## 2. Ротация пароля прод-базы

**Зачем.** Пароль засветился 16 августа 2026 и с тех пор не менялся. База —
управляемый Postgres, бэкенд ходит в неё по `DB_*` из `.env` на прод-дроплете
(адрес — в личных заметках владельца, в репозитории его нет); пароля в
репозитории нет и не было.

**Порядок. Он важен: между сменой пароля в базе и правкой `.env` бэкенд
отвечает 500 на каждый запрос.** Окно надо сделать минутным, а не
«пока не найду файл».

1. **Сначала подготовить всё, что понадобится:** новый пароль сгенерирован,
   доступ к панели базы открыт, ssh на дроплет открыт, путь к `.env` найден:

   ```bash
   ssh <пользователь>@<адрес прод-дроплета>
   cd /opt/trip-track-backend && ls -l .env
   cp .env .env.bak.$(date +%F)     # откат в одну команду
   ```

2. **Сменить пароль пользователя базы** — в панели управляемой базы либо
   вручную:

   ```sql
   ALTER USER "<пользователь>" WITH PASSWORD '<новый пароль>';
   ```

   Старые открытые соединения при этом НЕ рвутся: Postgres проверяет пароль
   на установлении соединения. То есть приложение продолжит работать до
   первого переподключения — это и есть запас времени, а не признак того, что
   всё в порядке.

3. **Поправить `DB_PASS` в `/opt/trip-track-backend/.env`** и перезапустить:

   ```bash
   docker compose up -d --force-recreate app
   docker compose logs --tail 50 app        # ищем «Nest application successfully started»
   curl -s localhost:3003/health
   ```

4. **Проверить снаружи** — `https://api.trip-track.app/health` и любой экран
   приложения, которому нужна сеть (лента).

5. Убедившись, что всё живо, **удалить `.env.bak.*`**: это файл с СТАРЫМ
   паролем, и лежать он должен ровно столько, сколько нужно на откат.

**Откат:** вернуть `.env` из бэкапа и поставить в базе прежний пароль тем же
`ALTER USER`. Пока старый пароль не заменён третьим — откат возможен.

**Чего НЕ надо делать:** менять пароль «на ходу» в пятницу вечером и без
открытого ssh. Единственный способ починить неудачную ротацию — попасть на
машину, и если ssh в этот момент не открыт, сервис лежит до тех пор, пока не
откроется.
